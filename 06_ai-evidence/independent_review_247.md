# 复核：246配置门槛阻断与P2 AXI模块

2026-10-18。对象：`deliveries/opus246_config_gate_blocker_20261018_v1/`、`deliveries/p2_axi_pc_module_20261018_v1/`。读了候选`p1_gp_control.sv`第40—50、104—135行，`p1_probe.py`第156—212行，三个`config_gate_*.stdout`，P2的`README.md`、`MODULE_RESULT.json`、`axi_pipeline_sim_verified.json`摘要。只读，未连板卡。

## 1. 研发方指出的问题成立，246需要修正

我在246只看了释放判定，漏掉了硬件写门槛：`config_allowed=!enable_gp&&fence_gp&&!busy_gp`（第48行），而`fence_gp`依赖包含原生视频活动的`fence_hp`。描述符五个寄存器（第124—130行）和CLEAR（第113行）都要求它，被拒的写会置`rejected_gp`并让epoch加1。仿真（三组时钟相位，状态0x440→写BASE读回0、CLEAR未接受、STATUS 0x460）确认了这一点。**246的0x359只能作为释放判定，不能作为配置许可。** 这是我的遗漏。

epoch的解释也同意：“epoch非0即拒绝”只适用于上电gate（B2）。运行中每次本地写（包括被拒的写）都会使epoch加1，prepare/reclaim/release应要求两份样本epoch相同且等于本次操作前记录的当前值。

## 2. 不改RTL的修正方法

从RTL看，**只有配置写和CLEAR需要硬件fence**；`START_ENABLE=1`（第121行）和`START`（第109行）只要求`!busy_gp&&!quarantine_gp`，不需要fence。START本身会清掉`done_gp`和`has_error_gp`。112帧使用同一个私有租约，源/目的地址和长度都不变。所以：

1. **把配置许可和释放许可分开。** 释放仍按246的P1自身谓词。配置只在开始复制前做**一次**，之后每帧不再写描述符、不再CLEAR。
2. **配置阶段**（租约创建之后、第一次START之前）：对五个寄存器逐个执行“等待硬件完整fence（0xfd9==0xc0，两份相同epoch）→写一次→立即读回”。读回不对就回到等待，同一寄存器总尝试次数和总时间设上限（建议每个寄存器≤20次、整个配置阶段≤30s）。五个都读回正确后，同样在fence下发一次CLEAR，要求`completed_seq`前进且rejected变为0。这是被拒写的有限次重试，**只在没有任何DMA、没有所有权变化的配置阶段允许**，与“任务不自动重试”不冲突，但必须在计划里写明次数上限。
3. **配置阶段失败**（到上限仍未完成）：P1从未START，按P1自身谓词确认空闲后正常释放租约，记为“配置窗口不足”，不需要断电，也不是UNKNOWN。
4. **每帧**：读回五个描述符确认未变 → 按P1自身谓词确认空闲 → `START_ENABLE=1` → `START` → 等done → `START_ENABLE=0` → 按P1自身谓词确认空闲 → reclaim/比较。每帧开始前要求rejected为0（配置阶段的CLEAR已清掉），之后任何新的rejected都按错误停止。
5. 采样器在配置阶段把每段连续0xC0的长度和间隔记录下来。能否成功，取决于原生空闲窗口是否长于“同步延迟＋一次Python MMIO读写”的时间。本轮16个样本中有3个0xC0，说明窗口存在，但长度未知。

这一方法仍然是同一候选、不改RTL。它改变了246的执行方式，属于“方法变化”，研发方实现后**封存时附上对应PC控制即可，不需要再单独送审**。PC控制至少覆盖：原生读持续时配置写被拒并有界退出；配置阶段失败后租约被正常释放；每帧不写配置、不CLEAR；rejected残留时拒绝START；epoch按“当前值”比较。

## 3. 同时准备根本修正（与P2集成合并）

P2接入父设计必然要生成新bit，到那时把`config_allowed`改为只依赖P1自身状态（`!enable_gp&&!pending_gp&&!busy_gp&&!quarantine_gp`加上同步后的`!core_busy&&!rout&&!wout&&!fault_hp`），原`fence_hp`位保留作诊断。这样不额外增加一次重建。

建议顺序：

- 先按第2节用现有候选申请一次上板（同一套预算：候选1、回退1、112复制、1000帧NPU）。如果配置窗口不足，按第2.3条安全释放、走冷回退，不再追加尝试。
- 研发方同时在PC上把配置门槛修改并入P2集成工程。如果第一项失败，就直接用集成bit验证P1复制和P2，不再为P1单独出候选。

## 4. P2 AXI模块

PC功能结果可信：23项（17项定向负向用例，7帧完整尺寸），逐字节与已有CPU golden比较8,601,600字节；最后一个B延迟≥64周期，检验了不会提前报完成；同一帧连续处理两次不复位；STOP/超时/错误ID保守隔离，不自动恢复。OOC为1117 LUT、612 FF，内部寄存器间setup +0.411、hold +0.130ns；整体hold −0.015ns、51个端点，原因与上次相同（OOC边界假设），接入父设计后以完整时序为准。不阻断。

**需要提前知道的一点**：模块为单拍、每方向最多一个事务。按HP2每拍往返大约十几到几十个周期估算，一帧6.2MB读入加1.2MB写出可能需要几十到上百毫秒，明显慢于CPU取样。这不影响功能验收，但P3做“CPU与PL对比”时，结论很可能是PL更慢。如果时间允许，可以把读方向改为突发（LEN最大15），这是最主要的提速点；不改的话，报告中如实写“功能正确，未做带宽优化”。

## 5. 结论

- 246第3节修正为：释放用P1自身谓词，配置用硬件fence并按第2节只做一次。
- 研发方可以按第2节实现、封存、向用户申请新预算，不再单独送审。
- 配置门槛的RTL修正并入P2集成bit。
- 下一个送审节点仍是“P1实板结果出来之后”。
